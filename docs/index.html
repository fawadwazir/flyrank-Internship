Which Page Gets Refreshed First? Scoring Content Decline Under an Honest Client-Holdout Split

Fawad Wazir BS Artificial Intelligence, University of Science & Technology Bannu September 2026 Repository →

Abstract. Which of a client's existing pages should an editor refresh first, out of thousands that could plausibly qualify? This paper builds a page-level scoring model on FlyRank's content performance dataset and evaluates it against a transparent three-gate baseline rule (stale + strikable + visible) using a held-out set of clients the model never trained on. On that honest split, a logistic regression scorer roughly doubles the baseline's precision at the top of the queue (Precision@50: 0.34 → 0.74) while a more complex Random Forest does not improve on the simple model — and the Random Forest's apparent 0.92 Precision@50 disappears to 0.56 the moment the split stops leaking client identity, which is itself the paper's central finding. The output is a ranked, reason-coded refresh queue meant to sit in front of a human editor, not to replace one.

1Introduction & Problem Statement

A content team managing dozens of clients cannot manually review every page every quarter to decide what to refresh. They need a ranked, defensible worklist. The unit of analysis is one page belonging to one client, scored on its trailing 90-day performance. The output is a three-tier queue (refresh_priority, refresh_backlog, no_action) with a short reason code per page. The action a human takes is working the priority tier first. A false positive costs an editor's time; a false negative lets a real opportunity keep losing traffic unnoticed — neither is catastrophic, which is why this is built as a prioritization aid reviewed by a person, not an automated trigger.

2Data

This paper uses data/raw/content_refresh_anonymized.csv — a 30,000-row, 32-client starter slice (52 columns: identifiers, content metadata, 90-day performance metrics, and pre-computed trend/tier fields). All identifiers are pre-anonymized hashes.

The internship's data contract scoped a label definition against the full 79M-row FlyRank/internship-warehouse release on Hugging Face. This iteration was built and evaluated on the 30,000-row starter slice — the same slice the baseline was validated on — so baseline and model are compared on identical data. Scaling this exact pipeline to the full warehouse is listed as future work (§8).

Excluded on purpose: trend_direction / trend_pct (the label, or derived directly from it); the paired 30-day impression/click/session columns the label is computed from; and both ID columns, used only for grouping, never as features. No client name, URL, or query string appears anywhere in this repo.

3Methodology

Baseline

A transparent, non-fitted three-gate rule: flag a page only if it is stale (freshness_tier == "91-180"), strikable (position_tier in page_1/striking), and visible (impression_tier in moderate/good/excellent); rank flagged pages by raw impressions_90d.

Target

is_declining_label = 1 if trend_direction == "down" — a proxy for "this page's traffic is trending down," not a guarantee of a future outcome.

Features

18 numeric (standardized) + 8 categorical (one-hot) = 26 features spanning volume, competition, content shape, visibility consistency, position, and engagement. Full list and exclusions in the repo's work/capstone_report.md §4.

Models & validation design

Logistic Regression and Random Forest, trained and compared on identical features and splits. The primary split is grouped by client_id (GroupShuffleSplit, 75/25, seed=42): 24 training clients (22,885 pages) vs. 8 held-out test clients (7,115 pages) the model never saw during training. A page-level random split was deliberately rejected as the primary evaluation — see §5.

Leakage checks

An automated assertion in the training script blocks the label column, the label's raw components, and both ID columns from ever entering the feature list. Client-holdout grouping is itself a leakage control: it prevents the model from partly memorizing per-client patterns instead of learning signals that generalize to a new client.

4Results

Test-set base rate: 51.7% (train: 55.0%) — close enough that the split isn't skewed. Logistic Regression wins on every metric, roughly doubling the baseline's Precision@50.

The split-honesty check The same Random Forest, same features, evaluated on a random 75/25 row split instead of client-holdout, scores ROC AUC 0.753, Precision@50 0.92 — a result that looks like a clear win. That gap (0.603 → 0.753 AUC) isn't a better model; it's the model partly recognizing clients it already saw in training. Any Precision@K number quoted on this kind of data without stating the split type should be treated with suspicion.

What the model found

Top Logistic Regression weights: higher 90-day impressions and a "good" (not "excellent") visibility tier raise flagged risk; a striking-distance position and higher clicks are protective; staleness in the 3–6 month range confirms the baseline's core intuition. Random Forest's top features — visibility consistency (days_with_impressions), content age, and position — tell a consistent story independently.

Error analysis

Of the model's top 50 ranked test pages, 37 (74%) are true declining pages, matching Precision@50 exactly. Two clients account for 35 of the 50 top picks — the same per-client concentration weakness the baseline had (see recommendations, §6). Most of the 13 false positives share a recently-updated freshness tier with a strong position but only low-to-moderate visibility — pages that look "at risk" on paper but haven't started declining yet.

5Limitations & Honest Framing

  • Proxy label, not ground truth. is_declining_label reflects a trend computed from two 90-day windows, not a verified cause of decline.
  • Directional, not causal. This model estimates association with a declining trend; it does not show that refreshing a flagged page causes a recovery. That would require a pre/post or holdout experiment.
  • Small client pool. 32 clients total (24 train / 8 test) is a thin base for a client-holdout evaluation; results should be treated as an early signal, not a settled number, until validated on the full warehouse.
  • Per-client concentration. Both the baseline and the model over-represent 2–4 clients at the top of the queue — a real deployment needs a fairness/quota constraint, not just a raw score sort.
  • Complexity didn't help here. Random Forest underperformed the simpler linear model on this feature set and sample size — reported as a genuine finding, not tuned away.

6Ranked Recommendations

  1. Adopt the Logistic Regression queue as the refresh worklist, reviewed by a human before any page is touched — it roughly doubles the baseline's hit rate on a fair evaluation.
  2. Cap how many pages any single client contributes to the top of the queue. Without a per-client quota, editors serving many clients will keep re-refreshing the same few accounts.
  3. Work the tiers in order — refresh_priority this sprint, refresh_backlog next sprint, skip no_action.
  4. Re-validate quarterly — search behavior and competitive tiers shift; refit rather than assume stability.
  5. Never quote Precision@K without stating the split type — given the gap in §4, numbers from this dataset aren't comparable without that context.
